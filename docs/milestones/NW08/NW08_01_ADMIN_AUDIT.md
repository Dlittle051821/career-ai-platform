# NW08.1 — Existing Admin & Operations Audit

## 0. Purpose and method

Before any NW08 design or code, this document inventories what `/admin` already does today against the NW08 brief's 6 mockup areas (Command Centre, Student CRM, Counsellor & Team, Application Operations, Commercial/Finance, Mobile) and names, for each required capability, one of: **FULLY_FUNCTIONAL**, **PARTIALLY_IMPLEMENTED**, **NEEDS_UI_INTEGRATION** (data exists, no matching page/section yet), **NEEDS_BACKEND_INTEGRATION** (UI pattern exists, needs a new aggregate), **BLOCKED_BY_MIGRATION**, or **MISSING**. This classification is the basis for NW08.2–NW08.7's "reuse, don't duplicate" plan. No code was written for this document — it is a read-only audit of the repository as staged at `/home/claude/carrier.ai`, which is not a git repository in this sandbox (confirmed via `git status`/`git branch --show-current`/`git log -1`/`git rev-parse --is-inside-work-tree`, all `fatal: not a git repository`), consistent with every prior milestone this session.

**Headline finding:** `/admin` is already a mature, 21-nav-item, 18-route-directory system (`src/components/admin/AdminShell.tsx`). NW08 is substantially a **redesign + reorganize + extend** task, not a build-from-scratch task. The brief's own Section 1 instruction — "Do not create a parallel admin product" — is easy to honor here because almost everything NW08 needs to *read* already has a bounded, tested, documented query function; what's missing is mostly presentation (the mockup's visual language), a handful of genuinely new aggregates, and some IA regrouping.

## 1. Route & permission inventory (current state)

21 nav items in `ADMIN_NAV` (`AdminShell.tsx`), each gated by a specific `AdminPermission` from the 6-role matrix in `src/lib/admin/permissions.ts` (`super_admin`, `admin`, `counsellor`, `finance`, `content_editor`, `analyst`): Dashboard (`dashboard:read`), Students, Universities, Courses, Data Imports, Duplicates, Data Quality, Sources, Applications (`applications:read`), Leads (`leads:read`), Discovery Sessions, Pricing (`pricing:read`), Payments (`payments:read`), Invoices (`invoices:read`), Refunds (`refunds:read`), Payment Events, Billing Settings, Agreements, Counsellors (`counsellors:read`), Analytics (`analytics:read`), Content, Audit Log (`audit:read`). Every page already does server-side role resolution (`requireAdminPermission()` / `getCurrentAdmin()`) — no client-supplied role/id/status field is trusted anywhere observed. NW08's suggested IA regrouping (Command Centre / Students & CRM / Applications / Counsellors & Team / Commercial / Finance / Operations / Reports & Analytics / Settings) must be implemented as a **presentation-layer regrouping of these same 21 items plus new ones**, never a route rename that breaks an existing bookmark/link, and never a permission weakening.

## 3. Student CRM & lifecycle (NW08.3)

`/admin/students` and `/admin/leads` already exist as separate, fully functional CRUD surfaces with their own canonical status enums (`AdminStudentStatus`: prospect/active/inactive/archived; `LeadStage`: new/contacted/qualified/nurturing/converted/lost — both in `src/types/admin.ts`). **Classification: PARTIALLY_IMPLEMENTED for the unified-CRM mockup view; FULLY_FUNCTIONAL for the underlying data.** NW08.3's job is a presentation-layer unification (a combined view/nav grouping) that maps onto these two existing, untouched status models — the brief's own suggested 10-stage "conceptual lifecycle" is a **display-only re-labeling** of these real enums, never a new status column or a parallel lifecycle state. A narrower "Student Relations" CRM role is **NOT implemented in this milestone** — documented here as a considered-and-deferred proposal (see §8) per the brief's own "if required" framing, since the existing `analyst`/`content_editor` roles already give a template for a narrow, read-mostly role should one be commissioned later.

## 4. Counsellor & Team Management (NW08.4)

`/admin/counsellors` (159-line page.tsx) already provides counsellor CRUD. `listCounsellorWorkload()` (dashboard.ts) already computes `assignedStudentCount`/`assignedLeadCount`/`assignedApplicationCount` per counsellor. **Classification: FULLY_FUNCTIONAL for CRUD and workload counts; NEEDS_UI_INTEGRATION for a dedicated Team Overview page and Assignment Management UI** (the mockup's team panel groups workload + specialization + capacity in one view no current page shows together). Task Queue: `application_tasks` (NW06) is the one real task table in this codebase — any "staff task queue" NW08 shows **must** read from here (and, where unapplied, from NW07's proposed `recommendation_drafts`), never create a second task table. Per NW07's own handoff note, `recommendation_drafts` remains **BLOCKED_BY_MIGRATION** (unapplied) — any NW08 surface referencing counsellor recommendation-review workload must show a truthful "unavailable" state for that slice, not a fabricated count.

## 5. Application Operations (NW08.5)

`/admin/applications` (221-line list + 365-line detail page) is already a mature CRUD+detail surface covering stage, decision status, deadlines, submission tracking (`ApplicationSubmission`, Milestone 19), documents, checklist items, and notes. **Classification: FULLY_FUNCTIONAL for the underlying case data; NEEDS_UI_INTEGRATION for an operations-overview layer** the mockup wants (a cross-case table with exception flags) — this sits *above* the existing list/detail pages, reusing `listApplications()`/`getApplicationById()`, never replacing them. Accuracy rules already enforced in the existing code and to be preserved verbatim in any new overview: submission is only ever recorded via `submittedAt`/`ApplicationSubmission` (never inferred from shortlist or student self-report alone — see `submittedByUserId`/`internalNote` STAFF-ONLY fields), and Nextwise's "we never collect university/visa/government fees directly" boundary (NW06 `external_payment` task type) is untouched by NW08.

## 6. Commercial Operations & Finance (NW08.6)

`src/lib/supabase/admin/{payments,invoices,refunds,pricing}.ts` are all mature, independently CRUD-complete modules. **This audit's key finding for NW08.6, resolving the open question from NW08.1's earlier pass:** the codebase has **two distinct, non-interchangeable refund-status concepts**, and any Commercial/Finance dashboard must keep them visually and semantically separate per brief §9/§16:

- `Payment.refundStatus` (`src/types/admin.ts`) — a coarse 4-value summary field (`none | requested | partial | full`) living directly on a `Payment` record, read-only context for admins browsing payments.
- The standalone `refunds` table's own `status` (`src/types/payments.ts`) — the real, 8-value, RPC-driven lifecycle (`requested → under_review → approved → processing → processed | failed`, plus `rejected`/`cancelled`), enforced by `REFUND_STATUS_TRANSITIONS` (`src/lib/admin/status.ts`) and, for the two money-moving transitions (`processing→processed`/`failed`), by database-side `claim_refund_for_processing()`/`finalize_refund()` RPCs with race-safe conditional updates — **not** application-code arithmetic.

**Classification:** FULLY_FUNCTIONAL for all four modules' CRUD and the refund financial-safety mechanics (confirmed via full read of `refunds.ts`: gateway-check-before-claim ordering, uncertain-outcome handling that never guesses, exactly-once finalization). **NEEDS_BACKEND_INTEGRATION** for a unifying finance-dashboard aggregation layer (a "pending refund case count," a "refund value in flight," per-currency invoice/payment summaries side by side) — this is a thin new composition over the four existing modules, never a second ledger, and it must keep purchase/invoice/payment/refund/entitlement as four distinct concepts on screen (a `requested` refund case is never shown as money already returned; a `pending` payment is never counted as revenue — both already correctly excluded by `sumRecordedRevenue()`'s `status === "paid"` filter). The **GST/checkout-risk blocker is reconfirmed open and untouched**: no code in `payments.ts`/the checkout flow was read, modified, or exercised by this audit, and NW08 will not modify any payment calculation.

## 7. Analytics & Operational Reporting (NW08.7)

`/admin/analytics` (320 lines) already implements time-range filtering (All/7/30/90 days), lead funnel, application stage distribution, payment status distribution + per-currency revenue, counsellor workload, top lead sources/universities, and a full Milestone-9 product-metrics block (registrations, profile completion, event counts via `PRODUCT_EVENTS`, outcome distribution) — all built on the pure, unit-tested helper module `src/lib/admin/analytics.ts` (`computeRate()` with its `MIN_RELIABLE_SAMPLE_SIZE = 5` "not enough data yet" convention, `withShareOfTotal()`, `sumRecordedRevenue()`). **Classification: FULLY_FUNCTIONAL for everything it already computes; PARTIALLY_IMPLEMENTED against the brief's fuller ask** — current filtering is trailing-days only (no calendar month / custom range), and there is no written Metric Dictionary yet (brief requires `NW08_METRIC_DICTIONARY.md`, a new document type not produced by any prior milestone). No chart/visualization dependency exists in `package.json` (confirmed — no `recharts`/`d3`/`victory`/`visx`/chart.js match in dependencies or devDependencies); NW08 will build simple, accessible, inline-SVG/CSS visuals rather than introduce a new runtime dependency, matching the brief's own "avoid a heavyweight library" instruction.

## 8. Role model — "Student Relations" narrower role (deferred proposal)

The brief's NW08.3 section suggests a narrower CRM-only staff role. Decision for this milestone: **not implemented.** Reasoning: the brief itself only says "if new staff roles are required" (conditional, not mandatory), implementing it would require a new migration (new RLS surface, another `ROLE_PERMISSIONS` entry) which increases this milestone's database-change footprint beyond what the brief's own reuse-first/non-destructive-only mandate asks for, and nothing evidenced in the existing codebase shows a real operational need for it yet (every current CRM-adjacent task is already covered by `admin`, `counsellor`, or `analyst`). **Proposal, for a future milestone:** a `student_relations` role with `students:read/write`, `leads:read/write`, `dashboard:read` only — explicitly excluding `payments:*`, `pricing:*`, `refunds:*`, `counsellors:*` — added to `ADMIN_ROLES`/`ROLE_PERMISSIONS` the same way `analyst` was added, with its own narrow migration. This is documentation only; no code or migration for this role exists in NW08.

## 9. Test coverage inventory

Existing admin-area test files (all pre-NW08): `src/lib/admin/{analytics,audit,content,money,pagination,permissions,status}.test.ts`, `src/lib/supabase/admin/{application-checklist,application-documents,application-notes,application-submissions,applications,dashboard-work-queue,refunds}.test.ts`. No test file yet exists for `dashboard.ts`'s `getAdminDashboardSummary()` or `analytics.ts`'s `getAnalyticsSummary()` themselves (their pure-logic dependencies in `src/lib/admin/analytics.ts` are tested; the Supabase-calling wrapper functions are not — consistent with this codebase's general pattern of unit-testing the pure logic and leaving the thin DB-calling layer to structural review, as NW06/NW07 also disclosed). NW08.8 will add tests for every new pure aggregation function this milestone introduces (revenue trend bucketing, service-delivery composite, operational-alerts composition), following the same pure/testable-core pattern.

## 10. Conclusion — what NW08 must actually build

Net new, real engineering work for this milestone, all additive and reuse-first:
1. A small set of new, bounded, pure-logic-tested aggregate functions: revenue trend (time-bucketed, per-currency), service-delivery composite distribution, pending-refunds-in-flight count, operational alerts composition.
2. A visual/structural redesign of `/admin`'s dashboard page and `AdminShell` nav grouping to match the approved mockup's visual language, with the new KPIs above layered onto the existing 8.
3. Three new overview-layer pages (Student CRM unification, Counsellor & Team overview, Application Operations overview) that compose existing list/detail functions — no new CRUD primitives, no new tables.
4. A Commercial/Finance dashboard composing the four existing commercial modules, preserving the Payment.refundStatus vs. refunds.status distinction documented in §6.
5. An Analytics extension: calendar/custom date-range filtering, a documented Metric Dictionary, and the brief's 5-category + Executive Summary structure layered onto the existing, already-correct computations.
6. Full regression, new tests for everything in (1), security review, the 13-document set, and packaging — NW08.8.

Nothing above requires a new database table or a new migration. If a future design decision in NW08.2–NW08.7 surfaces a genuine need for one (it is not expected to), it will be proposed-only, non-destructive, and disclosed exactly as NW06/NW07's proposed migrations were.
