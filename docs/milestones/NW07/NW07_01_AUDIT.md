# NW07.1 — Existing Counselling System Audit

**Status:** Complete. This audit drives every later NW07 stage's scope — read it before NW07.2-08.

## 1. Methodology

Direct source reading, not assumption: every `/admin/*` route touching students/counsellors/discovery sessions/verification/recommendations was read in full, every relevant migration (`0004`, `0012`, `0013`, `0014`) was read in full, and the data-access layer (`src/lib/supabase/admin/*.ts`) each page calls was read in full. No capability below is classified from a filename or a comment alone.

## 2. The governing finding: the security model is real RLS, not a service-role bypass

`src/lib/supabase/server.ts`'s `createClient()` — the one client every `/admin/*` page and every `src/lib/supabase/admin/*.ts` function uses — is built with the Supabase **publishable (anon) key** plus the caller's own session cookies. There is no service-role client anywhere in the admin read/write path. **Every `/admin/*` read is a real, RLS-evaluated query as the signed-in user**, not an app-level filter dressed up as security. This means NW07's own "database security before production" requirement is already how this codebase works today — NW07's job is to extend this same model consistently, not bootstrap it from nothing.

`getCurrentAdmin()` (`src/lib/supabase/admin-auth.ts`), wrapped in React's `cache()` (per-request only), is the single place role/`counsellorId` is resolved, by querying `admin_roles`/`counsellors` as the caller — never from a client-supplied value. `requireAdminPermission()`/`requireAdminRole()` build on it and are called again inside every mutation, not just at the page level. NW07 reuses this exact function for its own auth — there is no second "who is this" resolver anywhere in this plan.

## 3. CRITICAL FINDING — the dual-basis counsellor-access model is NOT uniformly applied

Milestone 11-B2's own migration (`0014_discovery_session_counsellor_scope.sql`) establishes a **dual-basis** rule: a counsellor may access a student's case-adjacent data if EITHER (a) `admin_student_meta.assigned_counsellor_id = current_counsellor_id()` (a direct admin-granted assignment) **OR** (b) `discovery_sessions.assigned_counsellor_id = current_counsellor_id()` for some session belonging to that student (you ran their Discovery Session). 0014's own header comment explains why: `admin_student_meta` only accepts an INSERT from `super_admin`/`admin` — a counsellor can never become a student's assigned counsellor by themselves, so without basis (b) a counsellor who legitimately ran an unassigned student's Discovery Session would have no lawful way to act on what they learned.

**0014 applied this fix to exactly two tables**: `student_profile_section_provenance` and `student_recommendation_verifications`. Reading `0004_admin_system.sql` PART 12 directly shows the fix was never extended to the tables that actually carry the student's identity and case record:

- `public.profiles` (SELECT, line ~943) — single-basis only (`admin_student_meta` assignment).
- The entire 11-table Student Digital Profile family — `student_profiles`, `student_education`, `student_subject_strengths`, `student_interests`, `student_skills`, `student_work_preferences`, `student_career_priorities`, `student_career_goals`, `student_study_preferences`, `student_funding_preferences`, `student_experience` (generated via a `foreach` loop over exactly this array, lines 961-987) — single-basis only.
- `public.admin_student_meta` itself (SELECT, line 412) — single-basis only.
- `public.admin_student_notes` (SELECT + INSERT, lines 437/452) — single-basis only.

**Concrete consequence:** a counsellor who is `discovery_sessions.assigned_counsellor_id` for a student, but has never been given a formal `admin_student_meta` assignment (which only `super_admin`/`admin` can create), can today read that student's profile-section **provenance overrides** and **recommendation-verification overrides** — but cannot read the student's actual name/email (`profiles`), their actual academic/career data (the 11 `student_*` tables), their own `admin_student_meta` status row, or any internal note about them. `getStudentDetail()` would return a student with a null/empty profile for exactly this counsellor. This is the single most consequential gap for NW07.3 (Student Case Workspace): the Discovery Session flow this whole milestone showcases is precisely the flow where this gap bites.

**Why this happened (not a bug, a scope boundary 0014 drew on purpose):** 0014's own comment says it widened "ONLY the two M11-C policies" — a deliberate, narrow fix for the one feature (M11-B2) being built at the time, not a general-purpose widening. NW07 is the first milestone that actually needs the general case.

**Resolution this plan takes (see `NW07_DATABASE_CHANGE_PLAN.md`):** propose `NW07_counsellor_case_access_widening.sql` (unapplied), extending the exact same, already-reviewed 0014 pattern — same `drop policy if exists` / `create policy` shape, same dynamic-SQL loop technique for the 11-table array — to: `profiles` SELECT, all 11 `student_*` tables' SELECT, `admin_student_meta` SELECT, `admin_student_notes` SELECT + INSERT. Deliberately **not** touching `admin_student_meta`'s UPDATE policy (status/assignment changes) or any INSERT/UPDATE policy on the 11 student tables — those stay `super_admin`/`admin`-only or student-only exactly as today; a counsellor earning a discovery-session basis should be able to *see* the case and *add case artifacts* (notes, provenance, verification — all independently audited, attributable actions), never *become* the student's formal assigned counsellor or edit the student's self-reported data, which stays entirely out of scope for every milestone to date. Until this migration is reviewed and applied, NW07.3's Student Case Workspace **fails closed** for a discovery-session-only counsellor on the profile/academic tabs specifically (clearly labeled, never silently empty) — flagged as `BLOCKED_BY_MIGRATION` below, not claimed as working.

## 5. Routing decision: `/counsellor/*` as a new, distinctly-branded route tree over the SAME data-access layer

**Decision:** build `/counsellor/**` as its own route tree (own `layout.tsx`, own `CounsellorShell` nav mirroring the NW07 mockup — Dashboard/My Caseload/Discovery Sessions/Verifications/Recommendations/Tasks/Settings, with an Applications link to the existing NW06 surface where permitted), gated by the exact same `getCurrentAdmin()`/`requireAdminPermission()` functions `/admin/*` already uses — not a second auth system. Every read a `/counsellor/*` page needs is served by the **same** `src/lib/supabase/admin/*.ts` functions `/admin/*` already calls (`getStudentDetail`, `listDiscoverySessions`, `getDiscoverySessionWorkspace`, `listCounsellorOptions`, `getSectionProvenanceMap`, `getRecommendationReadinessForAdmin`, NW06's application-tasks reads) plus a small number of genuinely new, equally RLS-backed additions: a counsellor-dashboard aggregator, a per-student discovery-session list helper, and the new recommendation-workflow module (NW07.6).

**Why not extend `/admin/*` in place:** the mockup's Counsellor Studio is explicitly its own branded surface (distinct from the operational admin console that also serves finance/content_editor/analyst), mirroring this codebase's own existing precedent of `/studio` as the student-facing surface sitting beside (not inside) the public marketing site. Folding a counsellor-specific UX into `/admin/*`'s existing nav (which also shows Universities/Pricing/Billing/Education Imports — modules a pure counsellor has no permission for and should never have to navigate around) would be the wrong shape for the brief's own UI/UX section. `/admin/students/[id]`, `/admin/discovery-sessions/**`, `/admin/counsellors/**` are left completely unmodified by this decision — super_admin/admin/finance/analyst keep using them exactly as today; nothing already shipped is removed, renamed, or risked.

**Why this is not "a duplicate competing portal":** zero new tables are introduced for anything `/admin/*` already reads correctly; zero new RLS policies are introduced for anything already correctly scoped; the one schema gap found (§3) is fixed once, at the RLS layer, benefiting both `/admin/*` and `/counsellor/*` identically (an admin visiting `/admin/students/[id]` for a discovery-session-only case gets the same, newly-correct read). `/counsellor/*` is a presentation and workflow layer, not a second backend.
