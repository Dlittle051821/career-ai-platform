## 2. Area-by-area classification

### 2.1 Application data model & lifecycle — `EXISTING_AND_FUNCTIONAL`

`public.applications` (Milestone 7, `0004_admin_system.sql`) is the one and only application record in this codebase. Milestone 16 (`0017_student_application_workflow.sql`) extended it with a real 11-stage lifecycle (`inquiry → preparing → ready_to_submit → submitted → under_review → interview → decision_pending → offer_received → enrolled`, plus terminal `rejected`/`withdrawn`), `course_intake_id`/`student_note`/`submitted_at`/`decision_at`/`withdrawn_at` columns, a duplicate-active-application guard (two partial unique indexes), and — critically — **removed all direct student RLS access** to the table (v3 patch, PART 7), replacing it with three narrow `SECURITY DEFINER` RPCs:

- `student_start_application(course_id, university_id)` — the only way a student creates an application. Server-derives every protected field; verifies the course/university pairing against the same published+active gate the public course-browsing policy uses.
- `student_advance_application(application_id, action)` — the only way a student moves their own application (`start_preparing`/`mark_ready_to_submit`/`withdraw`; `submit` is a recognized-but-always-rejected action name — see §2.3).
- `student_update_application_note(application_id, note)` — the only way a student writes their own `student_note` (entirely separate from staff-internal `internal_notes`).
- `get_my_applications()` / `get_my_application(id)` / `get_my_application_status_history(id)` — the only student read paths, each with a `RETURNS TABLE` that structurally excludes `internal_notes`/`assigned_counsellor_id`/`last_contact_date`/history `note`/`changed_by`.

TypeScript orchestration: `src/lib/supabase/education/applications.ts` (student-facing, RPC-only), `src/lib/supabase/admin/applications.ts` (staff-facing, direct-table with conditional-UPDATE optimistic-concurrency and audit logging). Pure logic: `src/lib/applications/application-lifecycle.ts` (stage buckets, progress bar, next-action copy, deadline resolution). Student UI: `src/app/(site)/applications/page.tsx` (bucketed list) and `src/app/(site)/applications/[id]/page.tsx` (full detail: timeline, documents, note, history, next-step action). Admin UI: `src/app/admin/applications/page.tsx` (filterable/paginated queue with work-queue-bucket grouping) and `src/app/admin/applications/[id]/page.tsx` (full processing workspace). Decision outcomes (`decision_status`: `pending/offer/waitlist/rejected/deferred`, plus free-text `offer_type`) are staff-only-writable via the admin form; a student never sets either.

This single system already serves **both** Career and Abroad applications — NW05 already built `/studio/abroad`'s Application Journey card by filtering this same `listMyApplications()` output through `isAbroadDestinationName(universityCountryName)`. NW06 does not need (and must not build) a second, Abroad-only application table.

### 2.2 Secure document storage — `EXISTING_AND_FUNCTIONAL`

Milestone 17 (`0018_application_documents_foundation.sql`, v3) built `public.application_documents` with: zero direct student RLS access of any kind (every read/write is RPC-only); a private Storage bucket (`application-documents`, 25MB limit, 4 allowed MIME types, provisioned idempotently from the migration itself); server-generated, non-guessable storage paths (`<application_id>/<random uuid>/<sanitized filename>` — the client never supplies or picks the path); a Storage SELECT policy that requires the object's path to match a **current** (`is_current = true`) metadata row, so a replaced/removed document's bytes become unreadable the instant its metadata is retired, independent of whether best-effort physical cleanup ever runs; a Storage DELETE policy that blocks direct deletion of any object still backing a current document; and three RPCs (`get_my_application_documents`, `student_upload_application_document`, `student_remove_application_document`) that re-verify ownership inside their own `WHERE`/lock, never trust a preceding read.

Milestone 18 (`0020_application_processing_workspace.sql`) added a three-state staff review workflow on the **same** table (`review_status`: `pending_review/accepted/needs_correction`, plus staff-only `review_note` and student-facing `correction_message`), via `staff_review_application_document()` — a single atomic conditional UPDATE, least-privilege-scoped to `super_admin`/`admin`/the assigned counsellor only (finance/analyst explicitly excluded after a v3 security review).

TypeScript: `src/lib/supabase/education/application-documents.ts` (student upload/remove/list, with an explicit error-message allow-list so no raw Postgres/Storage error ever reaches a student), `src/lib/supabase/admin/application-documents.ts` (staff list/review), `src/lib/applications/application-documents.ts` (pure 9-type taxonomy, 3-document required subset, completeness calculators). UI: embedded in both the student `/applications/[id]` page (`ApplicationDocuments` component — upload, replace, remove, see correction messages) and the admin processing workspace (`AdminDocumentReviewControls`, download via short-lived signed URL).

This already satisfies nearly every one of the brief's 20 document-security requirements verbatim: private bucket, ownership enforcement, no public read, short-lived signed URLs generated server-side only, no client-supplied-path trust, server-generated keys, type/size validation, no path traversal, no cross-student access, metadata/bytes separation, version handling (via `is_current`), access enforced on download not just listing, internal fields invisible to students. **Not present:** a declared malware-scanning step (there is none, and the codebase does not claim one — consistent with the brief's own "never claim scanning occurred if it didn't" instruction) and a formal retention/deletion policy document (operationally, nothing is ever hard-deleted — see §8 for whether this needs a new deliverable).

### 2.3 Submission evidence & the "students can never self-submit" invariant — `EXISTING_AND_FUNCTIONAL`

This is the brief's single most safety-critical requirement (Section 07: *"A student must never change authoritative submission or university decision status directly"*), and it already has **two independent layers of enforcement**, not one:

1. **Milestone 19** (`0021_application_submission_tracking.sql`) added `public.application_submissions` (one immutable row per application: method, platform, external reference/URL, staff-only internal note, `submitted_by_user_id` always `auth.uid()`) and `public.application_submission_documents` (an immutable snapshot of the exact accepted-document rows included, by row id — never by type, never re-resolved later). The only write path, `staff_record_application_submission()`, re-validates — inside one locked transaction, against the live database, never a value the caller read earlier — role/assignment, stage (`ready_to_submit` only), zero outstanding `needs_correction` documents, every required document type `accepted`, and every manual checklist item complete, before performing the stage transition and writing the audit trail. Explicitly documented as **never** implying Nextwise itself submitted anything — it only records that staff already did, manually, outside this product (matches the brief's own repeated instruction not to claim a university-portal integration).
2. **A follow-up correction migration**, `0022_authoritative_submission_invariant.sql`, found and closed a real gap in the v19 design: a student's own `student_advance_application('submit', …)` and the generic admin `updateApplication()` form could *both* independently reach `stage = 'submitted'` with **no** corresponding `application_submissions` row — an invariant violation. The fix is a database trigger (`applications_enforce_submitted_transition`) that blocks **any** UPDATE from any caller from setting `stage = 'submitted'` unless a transaction-local flag is set — and that flag is set, and immediately cleared, *only* inside `staff_record_application_submission()`, around its own one UPDATE statement. This is a genuine database-level backstop, not merely a hidden UI button: even a future code path nobody thought to audit, or a raw SQL statement run with table access, cannot create a fake "submitted" state. `student_advance_application()`'s `submit` action now always raises a clear, honest error instead of reaching this code path at all (defense in depth alongside the trigger, not instead of it).

This already exceeds what the brief asks for in Section 07/Section 19 (P0: "unauthorized submission status"). No new work is needed here; NW06 should document and preserve this exactly as built.

### 2.4 Counsellor/Admin processing workspace — `EXISTING_AND_FUNCTIONAL` (for the general, non-Abroad-specific case)

Milestone 18 built `application_checklist_items` (4 fixed manual items: `profile_reviewed`/`eligibility_checked`/`intake_confirmed`/`details_confirmed`, toggled only by an authorized staff member, `completed_by` always server-derived) and `application_internal_notes` (append-only, staff-only, mirrors the pre-existing `admin_student_notes` shape). `src/app/admin/applications/[id]/page.tsx` is a single, mature page combining: identity header, a sticky "next operational action" panel (`getNextOperationalAction()`), the editable `ApplicationForm` (stage/counsellor/decision), the readiness checklist, a "student action required" panel (re-reading the same correction-message/note data from the student's own side, framed for staff), the submission-preparation panel (gated behind `application-submissions:write`), documents with review controls, internal notes, and full stage history. `src/app/admin/applications/page.tsx` is a filterable (by student name/email, by stage), paginated queue with a sticky work-queue-bucket summary bar (`needs_action`/`waiting_on_student`/`ready_for_submission`/`awaiting_university`/`no_action`/`closed`).

Authorization is handled correctly throughout: `requireAdminPermission()`/`hasPermission()` gate every mutation server-side; a `counsellor` role's direct `applications` table queries are automatically RLS-scoped to `assigned_counsellor_id = current_counsellor_id()` (no separate "my queue" filter UI is needed because RLS already restricts the rows returned); `finance`/`analyst`/`content_editor` are explicitly excluded from document/checklist/notes/submission access (a deliberate least-privilege narrowing found during Milestone 17's own v3 security review). Internal notes and `internal_notes`/staff-only submission fields are never exposed through any student-facing query.

**What is genuinely missing here, specific to NW06's own scope:** none of this workspace is Abroad-aware — it operates on the single shared `applications` table regardless of destination country, which is correct (no second architecture should be built), but there is no staff-side surface for the new per-student **task** concept (§2.6) once it exists, since that concept does not exist yet anywhere in the codebase.

### 2.5 Student-facing application dashboard & detail pages — `PARTIALLY_IMPLEMENTED`

`/applications` (bucketed list: Active/Submitted/Decision/Closed, real counts, empty state) and `/applications/[id]` (progress timeline, details, documents, student note, submission record once staff have recorded one, history, next-step action) are real, data-driven, already-good pages — not the kind of thing that needs replacing. What they are **not** is the richer dashboard shape the NW06 mockup specifically shows (six-way status tiles with counts, an upcoming-deadlines list, a cross-application action-required panel, a recent-activity feed, and a status-filterable table) — that visual shape does not exist anywhere today, for either product, and `/applications` itself is intentionally product-agnostic (shows Career and Abroad applications side by side), which conflicts with NW05's own established "Career and Abroad are independent workspaces" discipline. NW05 already set the precedent for this exact problem by building `StudentJourneyOverview`/`AbroadReadinessCard` as new, Abroad-scoped components layered on top of existing data rather than modifying the shared dashboard — NW06.2 should do the same: a new Abroad-scoped dashboard route, reusing 100% of the read functions audited in §2.1–2.3, never a new query.

### 2.6 Student "Action Required" / task system — `MISSING`

There is no persisted, structured task/to-do model anywhere in this codebase. What exists today are three independent, ad hoc **signals**, each useful but none of them a task: (a) a document's `review_status = 'needs_correction'` plus its `correction_message` (one correction message per document, overwritten on the next review decision — no due date, no history of past corrections, no "mark as addressed" state beyond simply re-uploading); (b) `applications.next_action`/`next_action_date` (free-text, staff-typed, no fixed vocabulary, no completion state); (c) `getApplicationNextAction()`'s derived, single, stage-based copy string. None of these can represent the brief's own task vocabulary (`DOCUMENT_UPLOAD`/`DOCUMENT_REPLACEMENT`/`APPLICATION_REVIEW`/`APPLICATION_CORRECTION`/`EXTERNAL_PAYMENT`/`INFORMATION_REQUEST`/`OTHER_APPROVED_ACTION`), a `due_date`, a `creator`, a completion/verification lifecycle, or multiple concurrent open items per application. This is the single largest genuine new-build item in NW06 — see §8.

### 2.7 External university/visa/government payments — `MISSING`

Grepping the entire codebase for any concept of a third-party fee (`external_payment`, `university fee`, a "pay the university directly" flow) returns nothing. Every existing payment concept (`pricing_purchases`, `invoices`, `payment_transactions`, Razorpay integration) is exclusively about Nextwise's **own** commercial offerings (counselling packages) — there is no code path anywhere that could be mistaken for collecting a university application fee, a visa fee, or any other third-party charge, which is exactly the safe starting point the brief's Section 09 requires ("Nextwise does not collect…"). Nothing needs to be *removed* to satisfy that constraint; a new, narrow feature needs to be *added* so students have an honest, in-app way to see a verified fee amount/destination/instructions and acknowledge having paid it themselves, without Nextwise ever touching the money. See §8.

### 2.8 Shortlist vs. managed application — `EXISTING_AND_FUNCTIONAL` (the distinction already exists structurally; no enforcement of any numeric limit exists, by design)

`education_saved_items` (Milestone 9) and `applications` are, and always have been, two completely independent tables with no automatic conversion path in either direction — saving a university/course never creates an application row, and starting an application never touches `education_saved_items`. This already satisfies the brief's core NW06.3 requirement ("a shortlist must not auto-create a paid application") with zero new code. `student_start_application()` has **no entitlement check of any kind** today — any authenticated student may start an `inquiry`-stage application against any published course regardless of purchase history, for both Career and Abroad. There is also no concept anywhere in the pricing/entitlement model (`src/lib/products/entitlements.ts`, confirmed by direct re-read this audit) of a *numeric* allowance ("10 universities included," "3 extra applications") — entitlement today is purely binary (`hasAbroadEntitlement`/`hasCareerEntitlement`). Whether managed-application creation should require a paid entitlement is a genuine open product decision, not a technical gap — see §8 for why this audit does not silently add a paywall.

### 2.9 Notifications — `EXISTING_AND_FUNCTIONAL` (as a disclosed, honest placeholder)

`src/lib/notifications/notifier.ts` (Milestone 10) is, by its own docblock, **not** a real email/SMS/WhatsApp system — it is a `LoggingNotifier` that logs a structured line instead of sending anything, with a single documented swap-in point (`get-notifier.ts`) for a future real provider. `application_submitted`/`application_offer_received`/`application_rejected` templates already exist and already fire from the right call sites. This is the correct foundation to extend for any new task-created/payment-reminder notification (as a new named template, logged the same honest way) — never a claim that a message was actually delivered, per the brief's own explicit instruction.

### 2.10 Entitlements / commercial boundaries — `EXISTING_AND_FUNCTIONAL`

NW05's P0 fix (`getMyProductEntitlements()`, requiring a live `invoices.status = 'paid'` join, fail-closed) is unchanged and reusable as-is. The ₹1,999 GST-inclusive checkout calculation issue remains open, unresolved, and — per every prior milestone's own discipline — untouched by this audit and will remain untouched by NW06's implementation.

## 5. Decision: NW06's actual implementation scope

Given §1–§4, NW06 builds exactly four things, in addition to documentation:

1. **A new, Abroad-scoped Application Dashboard** (`/studio/abroad/applications`) — summary tiles, upcoming deadlines, a cross-application action-required panel (surfacing both outstanding document corrections and the new task system below), a recent-activity feed, and a status-filterable table — composed entirely from the existing, audited read functions in §2.1–2.3 plus the new task read function below. Zero new application-data queries.
2. **A new Student Action Required task system** (`public.application_tasks`) — the genuinely missing backend piece identified in §2.6, covering the brief's full task vocabulary, with student completion/staff verification, built on the exact same `SECURITY DEFINER` RPC + zero-direct-RLS pattern Milestones 16–19 already established (so it is architecturally consistent with everything that already exists, not a second convention).
3. **External university payment instructions**, as one task *type* within the same system (`EXTERNAL_PAYMENT`) rather than a parallel feature — never a Nextwise-collected payment, never an auto-verified "I paid" claim, matching §2.7 exactly.
4. **A minimal staff-side surface** to create/manage tasks on the existing admin application workspace (§2.4), gated by a new narrow permission pair following the established `"application-tasks:read"`/`"application-tasks:write"` convention — not a new workspace, an addition to the existing one.

Everything documented as `EXISTING_AND_FUNCTIONAL` above is reused as-is and re-verified by regression tests; none of it is rebuilt. Decision-outcome vocabulary (`decision_status`), submission-method vocabulary, and the document-type taxonomy are all left exactly as Milestones 16–19 defined them, per the brief's own "preserve established conventions" instruction and the already-good fit of each.

## 6. What NW06 explicitly will not do

- Will not add any entitlement/paywall check to `student_start_application()` or any numeric "package allowance" limit — no such limit is defined anywhere in the existing commercial configuration today, and inventing one would be exactly the "do not invent a new price / do not hardcode a limit" mistake the brief itself warns against. This is recorded as an open product decision for the business to make explicitly, not a gap NW06 silently closes.
- Will not touch payments, invoices, checkout, Razorpay, or pricing calculation in any way.
- Will not apply any migration to any database.
- Will not rebuild the Milestone 16–19 application lifecycle, document storage, submission tracking, or counsellor/admin workspace — all reused verbatim.
- Will not build the fuller NW07 Counsellor Studio.
- Will not commit, push, or deploy.

## 7. Risks / things to watch while implementing

- The new `application_tasks` table must follow the **same** "zero direct student RLS, narrow `SECURITY DEFINER` RPC for every read/write, `RETURNS TABLE` structurally excludes staff-only columns" discipline as every table since Milestone 16 v3 — this audit found that discipline was adopted specifically *because* the original Milestone 9-era direct-RLS approach kept leaking staff-only columns/trusting caller-supplied fields. Repeating the newer pattern from the start avoids re-learning that lesson.
- The external-payment task type must be constructed so that no code path can read as "Nextwise processed/received this money" — every field is staff-entered/verified informational text and a student acknowledgement checkbox, never a payment form, never a bank/UPI field, never a Razorpay order.
- The new dashboard must not silently show zero on a query failure (recoverable-error-state requirement) — every new read in NW06.2 reuses functions that already return safe empty defaults on error; the UI layer must distinguish "genuinely zero" from "failed to load" explicitly where the brief calls for it.

## 8. Items requiring explicit founder/admin product decisions (not resolved by this audit)

1. Should `student_start_application()` (or a future Abroad-specific equivalent) require a paid `hasAbroadEntitlement` before creating a *managed* application, and if so, from which stage? Today it is fully free, for both products, matching "free exploration retained."
2. What, if any, numeric per-package application allowance exists commercially? No such number is defined in code or in the pricing catalogue read during this audit.
3. Document retention/deletion policy for `application-documents` — operationally nothing is ever hard-deleted today (replacement/removal only flips `is_current`/`removed_at`); whether a real retention schedule is required is a compliance question outside engineering's authority to decide unilaterally.
