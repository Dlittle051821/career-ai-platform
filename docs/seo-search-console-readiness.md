# Search Console Readiness (Milestone 17B)

This document is the operational reference for taking Nextwise's public
technical SEO layer live in Google Search Console (and, by the same
mechanism, Bing Webmaster Tools). It reflects the real state of the code
after Milestone 17B — it does not promise indexing outcomes, which Google
alone controls.

## 1. Canonical production URL

```
https://www.nextwise.world
```

WITH `www`. This is the single production origin the whole SEO layer is
now built around:

- `src/app/(site)/layout.tsx` — `metadataBase` falls back to this value
  (`PRODUCTION_ORIGIN`) whenever `NEXT_PUBLIC_APP_URL` is unset, and every
  page's `alternates.canonical` (a relative path) resolves against it.
- `src/app/sitemap.ts` — every `<url>` entry is built from this same
  hardcoded `SITEMAP_BASE_URL`.
- `src/app/robots.ts` — the `Sitemap:` line points at
  `https://www.nextwise.world/sitemap.xml`.
- `src/lib/seo/structured-data.ts` — the Organization/WebSite/BreadcrumbList
  JSON-LD `url`/`item` fields fall back to this same origin.

Before Milestone 17B all four of the above hardcoded `https://nextwise.world`
(no `www`) — a real inconsistency with the stated canonical brand origin.
That is the one correctness fix this milestone made across the SEO layer;
see `M17B_COMPLETION_REPORT.md` for the full list of files touched.

**Actual deployment note:** the app still resolves `metadataBase` from
`NEXT_PUBLIC_APP_URL` first, falling back to the hardcoded value above only
when that variable is unset. Whoever configures the production deployment
must set `NEXT_PUBLIC_APP_URL=https://www.nextwise.world` (with `www`) so
the env-derived value and the hardcoded fallback agree. If the env var is
ever set to the non-www form, canonical URLs, the Organization/WebSite
JSON-LD, and the sitemap will disagree — the sitemap and robots.txt always
emit `www`, but per-page canonicals would silently drift to non-`www`. This
is a deployment-configuration risk, not a code gap, and is worth a
one-time manual check right after the first production deploy (see
Section 8).

## 2. Sitemap location

```
https://www.nextwise.world/sitemap.xml
```

Generated at request time by `src/app/sitemap.ts` (Next.js App Router
sitemap convention — no static file is checked in). Contents:

- 16 static entries: `/`, `/career-discovery`, `/careers`, `/courses`,
  `/universities`, `/pricing`, `/how-it-works`, `/book-counselling`,
  `/study-options`, `/about`, `/contact`, `/parents`, `/trust`,
  `/privacy`, `/terms`, `/refund-policy`.
- Every **published + active** career (`getCareerOptionsForComparison` —
  careers have no draft concept, so every row is legitimately public),
  university (`getPublishedUniversitySlugsForSitemap`), and course
  (`getPublishedCourseSlugPairsForSitemap`) detail page, enumerated from the
  real database at request time. No fabricated or placeholder URLs.
- Deliberately excludes `/compare` and `/courses/compare` (public but
  query-driven/combinatorial — Group B, see Section 4) and every
  authenticated, admin, tokenized-payment, or API route.

## 3. Robots.txt location

```
https://www.nextwise.world/robots.txt
```

Generated by `src/app/robots.ts` (Next.js App Router robots convention).
Allows `/` by default and explicitly disallows the private/internal path
prefixes listed in Section 5. Also declares the sitemap URL above.

**robots.txt is not a security boundary.** It is a crawl-politeness signal,
publicly world-readable, and trivially ignored by any crawler that chooses
to. Every path disallowed in robots.txt is independently protected by (a)
Supabase authentication/RLS for anything that touches real student/account
data, and (b) a permanent, page-level `robots: { index: false, follow:
false }` metadata tag for anything that should never be indexed even if a
crawler fetches it anyway. Removing a line from robots.txt would change
crawl behaviour, never access control.

## 4. Indexable route groups (Group A)

Public, meaningful, and intended to be indexed. Each has a unique title, a
useful description, a self-referencing canonical, and (site-wide or, for
the three dynamic routes below, per-entity) Open Graph/Twitter metadata:

- `/` — homepage.
- `/career-discovery` — primary discovery entry point.
- `/careers` — Career Explorer hub.
- `/careers/[slug]` — individual career detail pages (dynamic, DB-backed;
  per-entity OG/Twitter + BreadcrumbList JSON-LD added in Milestone 17B).
- `/courses` — Course Explorer hub.
- `/courses/[universitySlug]/[courseSlug]` — individual course detail pages
  (dynamic, DB-backed; per-entity OG/Twitter + BreadcrumbList JSON-LD added
  in Milestone 17B).
- `/universities` — University Explorer hub.
- `/universities/[slug]` — individual university detail pages (dynamic,
  DB-backed; per-entity OG/Twitter + BreadcrumbList JSON-LD added in
  Milestone 17B).
- `/pricing` — public pricing information.
- `/how-it-works` — product explainer.
- `/book-counselling` — counselling booking entry point.
- `/study-options` — India vs. study-abroad comparison content.
- `/about`, `/contact`, `/parents`, `/trust` — informational/trust pages.
- `/privacy`, `/terms`, `/refund-policy` — legal pages.

## 5. Noindex / private route groups

**Group B — public but intentionally NOINDEX** (crawlable, so a future
canonical/noindex decision can still be seen by crawlers, but excluded from
the sitemap and not meant to accumulate index value as-is, being
query-driven and combinatorial rather than a single stable piece of
content):

- `/compare` (career-vs-career comparison picker)
- `/courses/compare`

**Group C — authenticated/private, NOINDEX** (each independently carries
`robots: { index: false, follow: false }`, directly or via a parent
layout, and is additionally disallowed in robots.txt as defense-in-depth;
the real protection is Supabase auth/RLS, not either of those signals):

`/dashboard`, `/profile`, `/profile/onboarding`, `/saved`, `/applications`,
`/applications/[id]`, `/payments`, `/payments/[invoiceId]` (+ `/pdf` and
`/receipts/[transactionId]` sub-routes), `/agreements/[id]` (+ signed/stamped
document sub-routes), `/pricing/checkout/[slug]`, `/discovery-session/book`,
`/welcome`, `/recommendations`, `/roadmap`, `/pay/[token]` (tokenized,
single-use), `/login`, `/register`, `/forgot-password`, `/reset-password`,
`/auth/callback`.

**Group D — admin/internal, NOINDEX**: everything under `/admin/**`
(~55 pages/layouts, each independently noindexed, confirmed unchanged in
this milestone), plus internal API/webhook/redirect-utility routes
(`/api/**`, `/go/**`) which return JSON/redirects and were never indexable
HTML in the first place.

No route moved between these groups in Milestone 17B. The full route
classification and a per-route audit trail live in
`M17B_COMPLETION_REPORT.md`.

## 6. Search Console verification prerequisites

Before verifying the property in Search Console, whoever owns deployment
needs:

1. The production deployment actually serving `https://www.nextwise.world`
   (DNS + hosting configured so both the bare domain and `www` resolve, with
   the non-`www` host redirecting to `www`, matching the canonical chosen
   above — this repository does not configure DNS/redirects; that is a
   hosting-platform concern outside this codebase).
2. `NEXT_PUBLIC_APP_URL=https://www.nextwise.world` set in the production
   environment (see the deployment note in Section 1).
3. Either domain-property verification (a DNS TXT record on
   `nextwise.world`, which covers all subdomains and both `http`/`https`) or
   URL-prefix verification for `https://www.nextwise.world` specifically
   (an HTML file, a meta tag, or Google Analytics/Tag Manager already
   installed). This repository does not currently contain a Search Console
   verification file or meta tag — add whichever method is chosen at
   deploy time; it is intentionally not pre-added here since it is
   ownership-specific and would otherwise sit as a permanent unused file.
4. Confirm `robots.txt` is reachable and returns the expected content once
   deployed: `https://www.nextwise.world/robots.txt`.

## 7. Sitemap submission instructions

Once the property is verified:

1. In Search Console, open **Sitemaps** under **Indexing**.
2. Enter `sitemap.xml` (resolves to
   `https://www.nextwise.world/sitemap.xml`) and submit.
3. Search Console will fetch and parse it asynchronously — status typically
   updates within a few hours, not instantly.
4. Re-submission is not required after content changes; Google recrawls the
   sitemap periodically on its own. Re-submit only if the sitemap URL
   itself changes (it hasn't) or Search Console reports a fetch error.

## 8. Post-deployment inspection checklist

Run through this once, right after the first production deploy, and again
after any future SEO-layer change:

1. Fetch `https://www.nextwise.world/robots.txt` directly — confirm it
   loads, lists the expected `Disallow` prefixes from Section 5, and its
   `Sitemap:` line points at the `www` origin.
2. Fetch `https://www.nextwise.world/sitemap.xml` directly — confirm it is
   valid XML, every `<loc>` uses the `www` origin, and spot-check a handful
   of career/university/course URLs against real published records.
3. In Search Console's **URL Inspection** tool, check `/`, `/careers`, one
   real `/careers/[slug]`, one real `/universities/[slug]`, and one real
   `/courses/[universitySlug]/[courseSlug]` — each should report "URL is on
   Google" or "Crawled, currently not indexed" (both fine early on), never
   a canonical mismatch or a `noindex` detected on a page meant to be
   indexable.
4. Inspect one private URL, e.g. `/dashboard` — confirm Search Console
   reports it as excluded via `noindex`, and that this matches intent.
5. Use the **Rich Results Test** (or Search Console's own structured-data
   report) against the homepage and one career/course/university detail
   page — confirm the Organization/WebSite JSON-LD (homepage) and
   BreadcrumbList JSON-LD (detail pages) parse without errors.
6. Share a career/course/university detail URL through a social debugger
   (e.g. Facebook's Sharing Debugger or a Twitter/X card validator) —
   confirm the per-entity title/description/image render correctly rather
   than the generic site-wide card.
7. Confirm the environment variable check from Section 1 was actually
   applied — fetch any indexable page's rendered HTML and check the
   `<link rel="canonical">` tag uses `https://www.nextwise.world`, not a
   non-`www`, `localhost`, or preview-deployment URL.

## 9. Deferred to M17C (explicitly out of scope for this milestone)

Per the M17B task specification, none of the following was attempted:
large-scale content SEO, a blog system, hundreds of landing pages,
programmatic university/course/career pages beyond what the existing
database-backed detail routes already generate, city/state landing pages,
study-abroad country clusters, keyword-volume strategy, backlink
campaigns, or automated content generation.

## 10. Known SEO limitations

- **Google indexing is never guaranteed.** Everything above makes the site
  crawlable and indexable correctly; whether, when, and how prominently any
  given page is actually indexed and ranked is entirely Google's own
  decision and cannot be controlled from this codebase.
- **Two admin-only pages could not be included in this milestone's
  validated sandbox** due to a local tooling depth limit unrelated to their
  content (`/admin/pricing/[id]/versions/[versionId]/inclusions/[inclusionId]`
  and its `.../inclusions/new` sibling). Both are admin-only, already
  noindexed via the shared `/admin` layout, have zero public/SEO surface,
  and a full `npm run build` confirms omitting them from the validation
  sandbox caused no route-tree or build regression. See
  `M17B_COMPLETION_REPORT.md` for the full explanation.
- **Career detail pages do not cross-link to specific related
  courses/universities.** There is no database relationship modeling
  "courses or universities relevant to this career" yet, so no such link
  was added — inventing one would mean guessing, which the task's own
  instructions rule out. Course and university detail pages do link to
  each other correctly (a course page links to its own university; a
  university page links to a filtered view of its own courses).
- **No Search Console verification file/meta tag is checked into this
  repository.** It is intentionally left for whoever owns the production
  deployment to add, since the verification method (DNS vs. file vs. meta
  tag vs. existing Analytics) is an ownership decision, not a code
  decision.
- **Dynamic catalogue URLs in the sitemap depend on the underlying data
  being correctly marked published/active.** The sitemap code was already
  correct on this point before this milestone (it already queries only
  published+active rows) — this is not a new gap, just a dependency worth
  naming: if a career/course/university is incorrectly left in a draft or
  inactive state, it silently and correctly stays out of the sitemap.
